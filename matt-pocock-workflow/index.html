The premise
AI predicts an answer.
It doesn't guarantee one.
Without a workflow
You dump a vague prompt, get plausible-looking code, and discover the misunderstanding three files later.
With a workflow
Each step frames the next, errors surface early, and the output is measurable — so you can actually improve it.

Our worked example

We run one real feature through all five steps

IRL · a real feature, start to finish
Add “Forgot password?”
to the login screen
A user who forgets their password should get a reset link by email, click it, and set a new one — no emailing support, no admin resets.
01
Research

Reach shared
understanding first

/grill-with-docs · /wayfinder

The AI interviews you one question at a time until nothing is fuzzy. /wayfinder maps unknown territory and splits it so multiple agents research in parallel. No code until you both agree.

↘ In real life
grill › A reset link, or a 6-digit code?
you › A link. (emailed, single use)
grill › How long until it expires?
you › 30 minutes, then it's dead.
02
Spec

Write down
what gets built

/to-spec  (was /to-prd)

The agreed understanding becomes a specification — technical and business requirements in one doc. It fixes the boundaries of the change before anyone writes a line.

↘ In real life
spec.md — Password reset
  • “Forgot password?” → enter email
  • Email a single-use reset link
  • Link expires after 30 min
  • Opens a “set new password” page
  • Out of scope: SMS / 2FA
03
Tickets

Slice it into
shippable tasks

/to-tickets  (was /to-issues)

The spec becomes small, ordered tickets, each with its dependencies. Platform-neutral wording, so the same tickets land in Linear, GitHub, wherever.

↘ In real life
  • T1 — Generate & store a reset token (hashed, 30-min TTL)
  • T2 — POST /forgot → send the reset email (needs T1)
  • T3 — Reset page: validate token, set new password (needs T1)
04
Implement

Build ticket
by ticket

/implement

Test-driven where possible. Typecheck and run the single test file often; the full suite at the end. When the ticket is green, it hands straight off to review.

↘ In real life
1. test: an expired token → 400 (red ✗)
2. hash token, add 30-min expiry (green ✓)
3. typecheck · run the reset test file ✓
4. → route to /code-review
05
Review

Guard quality
& the spec

/code-review

Check correctness and spec alignment, then readability and maintainability. Catch bad patterns before the next AI agent copies them everywhere.

↘ In real life
  • Spec check — is the reset link truly single-use? Yes.
  • Security — token hashed at rest, never written to logs?
  • Correctness — expired and reused tokens both rejected?
The takeaway

Workflows evolve
through use.

measure it → find the friction → improve one step → repeat
